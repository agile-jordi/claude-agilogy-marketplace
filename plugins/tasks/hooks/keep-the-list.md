Keep this session's pending list with the tasks plugin's skills (`tasks:tasks-add`, `tasks:tasks-uncommitted`, `tasks:tasks-done`, `tasks:tasks-drop`, `tasks:tasks-document`, `tasks:tasks-delegate`, `tasks:tasks-archive`, `tasks:tasks-review`): add each open topic as soon as it appears (see `tasks:tasks-review` for what counts), mark it uncommitted when its work is done but not yet committed or pushed, and tick it when it is done. Once a change or feature is implemented, add a task to review it: compare what was done with the acceptance criteria, the document or the original prompt, item by item, to check that everything was really implemented, and tell the user what was left out.

- Owner: `claude` if Claude has to do it, `user` if the user has to (review, commit, decide, test).
- A task whose work ends in a commit is done once a merge request holds it: as soon as you finish the work, mark it uncommitted (also when the user says it is done but the commit is pending), and tick it done when the request exists and the commit is pushed to its branch, not when the request is merged. In a repo that takes no merge requests, tick it once committed.
- Every open merge request of this session's work has a task, owner `user`, to merge it (`merge-<n>`: "merge <repo> !<n>"): add it when you create the request, tick it once merged.
- Never add a task to pull, fast-forward or otherwise sync the user's main checkout (e.g. after pushing to the default branch), not even in a review: the main checkout is the user's. When CLAUDE.md allows pulling it to build it, do it on the spot, never as a task.
- When you find that an open task is already done (e.g. someone else did it), tick it without asking and tell the user, so they can correct you.
- Never print the list in a reply: the user sees it with `/tasks:tasks-show`.
